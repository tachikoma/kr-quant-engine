# 주문 원장(저널) 차단 해제 런북

대상 파일: `runtime_state/live_order_intents.json` (`LIVE_ORDER_JOURNAL`, gitignored)

## 1. 원장이란

러너는 브로커로 주문을 보내기 **전에** 의도를 원장에 기록합니다(`BROKER_SUBMISSION_UNCERTAIN`).
응답을 받으면 `ACKED`(접수, `order_id` 포함) 또는 `REJECTED`로 갱신합니다. 갱신에 실패해도 `UNCERTAIN`으로 남습니다.

- 항목 필드: `intent_id`, `trading_date`, `side`, `ticker`, `qty`, `attempt`, `status`, `order_id`(있으면)
- 자격증명·계좌 식별자는 기록하지 않습니다.
- **자동 삭제 조건**: 실행이 `DONE`이고 모든 주문이 접수·체결 확인되었으며 타임아웃·상태조회 오류가 없을 때만 러너가 스스로 지웁니다.
- 그 외(부분체결, 미체결, 접수 불명, 크래시, 상태조회 실패)에는 **파일이 남고**, 이후 LIVE 실행이 시작 시점에 막힙니다.
- 원장이 읽히지 않거나 형식이 깨진 경우에도 같은 방식으로 막힙니다(`unreadable/corrupt`).
- `LIVE_ORDER_ENABLED=0`(안전 모드/드라이런)에서는 이 검사를 하지 않습니다.

## 2. 차단 증상

러너가 시작 직후 다음 예외로 종료합니다(주문은 한 건도 나가지 않음).

```
Live order journal requires broker reconciliation: <경로>. Check orders/fills before manually archiving the journal.
```

또는 `Live order journal unreadable/corrupt ... manual reconciliation needed`.
실행 중 예외가 났다면 로그에 `[수동대조필요] 접수된 주문이 관리되지 않고 남아 있을 수 있음: ... order_id=...` 가 함께 남습니다.
종료 시 `[안전차단] 미확인 주문이 있어 원장을 유지합니다` 로그도 같은 신호입니다.

## 3. 하지 말 것

- **원장을 무조건 삭제하지 않습니다.** 이름 변경(보관)만 합니다.
- 증권사 주문·체결 내역을 확인하기 전에 해제하지 않습니다.
- "아마 안 나갔을 것"이라고 추정해 재주문하지 않습니다. 중복 방지가 우선이고, 자동 재주문은 하지 않습니다.
- 차단을 풀기 위해 `LIVE_ORDER_ENABLED=0`으로 돌려 놓고 상태 파일을 덮어쓰지 않습니다.

## 4. 대조 절차 (공통)

1. **자동 실행 정지.** 스케줄러/워크플로가 대조 중에 다시 돌지 않게 합니다(GitHub는 워크플로 Disable).
2. **원장 내용 확보.** 각 항목의 `trading_date`, `side`, `ticker`, `qty`, `status`, `order_id`를 기록합니다. GitHub 러너라면 해당 실행 로그의 `[수동대조필요]` 줄을 함께 모읍니다.
3. **증권사 내역 확인.** 앱/HTS/MTS 또는 증권사 주문조회에서 해당 날짜·종목의 **주문과 체결**을 모두 봅니다(미체결 잔량 포함). 확인 대상은 항목별로 다음과 같습니다.
   - `ACKED`: `order_id`로 조회해 체결/부분체결/미체결/취소 여부를 확인합니다.
   - `UNCERTAIN`: `order_id`가 없으므로 날짜·종목·방향·수량이 같은 주문이 있는지 찾습니다. **있으면 접수된 것으로 취급**합니다.
   - `REJECTED`: 증권사에도 주문이 없는지 확인합니다.
4. **항목별 판정.**

   | 증권사에서 확인된 상태 | 조치 |
   |---|---|
   | 주문 없음 (거절 포함) | 해제 가능 |
   | 전량 체결 | 해제 가능 |
   | 미체결 주문이 남아 있음 | **먼저 증권사에서 취소**하고 취소 완료를 확인한 뒤 해제 |
   | 부분체결 | 잔량을 취소하고, 체결된 수량을 보유와 맞춰 본 뒤 해제. 필요한 추가 매매는 사람이 판단 |
   | 확인 불가(조회 실패, 내역이 모호) | **해제하지 않음.** 증권사 고객센터 확인 후 재판단 |

5. **보유 대조.** 증권사 보유/현금이 러너 상태(`runtime_state/etf_daily_state.json`)와 모순되지 않는지 봅니다. 모순이면 해제 전에 원인을 먼저 정리합니다.
6. 모든 항목이 "해제 가능"일 때만 아래 5절로 진행합니다. 하나라도 아니면 원장은 그대로 둡니다.

## 5. 해제(보관)

### 5-1. VPS / 로컬

```bash
cd <repo>/runtime_state
mv live_order_intents.json live_order_intents.$(date +%Y%m%d).json.keep
```

- 삭제하지 않고 `.keep`으로 이름만 바꿉니다(감사 추적용). 같은 날 여러 번이면 시각을 덧붙입니다.
- 대조 결과(날짜, 확인한 증권사 내역, 판정, 확인자)를 `docs/` 또는 운영 노트에 남깁니다.
- 동시 실행 파일 락(`.etf_live_run.lock`)이 잡힌 프로세스가 없는지 확인한 뒤 옮깁니다.

### 5-2. GitHub Actions

러너는 `runtime_state/`를 `actions/cache`(키 NH `etf-daily-nh-state-<run_id>`, KIS `etf-daily-state-<run_id>`, `restore-keys` 접두어)로 이어 받습니다.
원장은 **그 캐시 안에** 있으므로 파일을 직접 옮길 수 없고, 원장이 든 캐시 항목을 삭제해야 합니다.

```bash
gh cache list --key etf-daily-nh-state-      # NH. KIS는 --key etf-daily-state-
gh cache delete <cache-id>                   # 원장이 생긴 실행 이후에 저장된 항목들
```

- `restore-keys`는 가장 최근 항목을 고르므로, 원장이 든 항목들만 지우면 그 이전의 깨끗한 캐시가 복원됩니다.
- **부작용**: 복원되는 캐시는 더 옛날 상태입니다(`last_rebalance_date`, 당일 완료 표시, 고점 자산 등이 과거 값). 그날 이미 주문한 상태라면 러너가 같은 날 다시 주문을 만들 수 있습니다. 삭제 전에 증권사 보유를 기준으로 영향을 확인하고, 필요하면 당일은 자동 실행을 켜지 않습니다.
- 삭제 전에 원장이 든 캐시의 실행 ID와 시각을 기록해 둡니다(삭제 후에는 복구할 수 없음).
- 원장 내용 자체는 4절 2단계에서 로그로 확보한 값이 유일한 기록일 수 있으니 먼저 저장합니다.

## 6. 재개 확인

1. 자동 실행을 다시 켜기 전에, 안전 모드(`LIVE_ORDER_ENABLED=0`)로 한 번 돌려 상태 로드와 계획 산출이 정상인지 봅니다.
2. LIVE 재개 후 첫 실행 로그에서 `requires broker reconciliation`이 **없는지**, 주문이 의도한 대로 나가는지 확인합니다.
3. 정상 완료되면 원장이 생성되었다가 자동 삭제되는 것이 정상입니다. 남아 있으면 다시 2절로 돌아갑니다.

## 7. GitHub Actions 저장 조건

러너는 예기치 않은 예외 시 종료 코드 1로 끝납니다. 예전 워크플로의 `Save runtime state`는 기본 조건(`success()`)이라 실패한 실행의 캐시를 저장하지 않았고, 그 결과 주문 전송 도중 예외로 생긴 원장이 다음 실행에 전달되지 않아 **차단 없이 진행**될 수 있었습니다.

- 이 PR에서 `daily_runner.yml`(KIS)과 `daily_runner_nh.yml`(NH)의 저장 단계에 `if: always() && hashFiles('runtime_state/**') != ''`를 추가했습니다. 실패·취소된 실행도 `runtime_state/`가 있으면 저장합니다.
- 이 변경이 `main`에 반영되기 전(또는 다른 브랜치)에 난 실패에는 적용되지 않습니다. 그런 실패는 GitHub 로그에서 `[수동대조필요]`와 `[원장]` 줄을 확인하고, 4절 대조를 **원장 파일이 없어도** 수행합니다.
- 실패한 실행이 저장한 캐시에 원장이 들어 있으면 다음 LIVE 실행이 차단됩니다. 이것이 의도된 동작이며 해제는 5-2절을 따릅니다.
