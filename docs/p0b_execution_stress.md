## 방법

| 축 | 구현 | 비용 중복 방지 |
|---|---|---|
| 슬리피지 | `run_etf_strategy(slippage=…)` 5/10/20/30/50bp | 별도 파라미터로만 적용 |
| 거래비용 배수 | `etf_shared.BUY/SELL_FEE_PCT`, `ETF_TAXABLE_SELL_TAX_PCT` × 1/2/3 | 슬리피지·스프레드에는 배수를 곱하지 않음 |
| 스프레드 | 주문 참조가격에 이미 포함(`SPREAD_PCT/2`) | 총비용에 **가산하지 않고** 참고값으로만 기록 |
| 유동성/규모 | `execution_mode="ohlcv_capacity"` (부분체결·1일 이월·취소) | 기존 정책 그대로 |
| 순위 안정성 | `scripts/parameter_stability.run_stability()` 재사용 (9개 인접 조합) | 동일 엔진·동일 데이터 |

실행 가드: `--start/--end`가 캐시 범위를 벗어나거나 `ETF_REFRESH_CACHE=1`이면 즉시 중단하고,
로딩 중에는 `fetch_etf_ohlcv_with_nav`/`get_stock`을 차단해 네트워크 조회와 캐시 쓰기를
원천 차단한다(캐시 시작보다 이른 구간은 상장일로 설명되는 경우만 허용).

비용 분해는 체결 내역에서 계산한다: `fee = 참조가격×수량×수수료율×배수`, `tax = estimated_tax`,
`slippage = 참조가격×수량×bp`, `total_run_rate_cost = fee + tax + slippage`.

## 검산 (모든 실행에서 강제)

- legacy: `equity == cash + market_value`(전 행), `final_cash == 초기자본 + Σcash_flow + Σ분배금`
  (허용오차는 거래 규모 기준 `scale×1e-12`; 잔여 현금 상쇄로 인한 float 오차만 허용)
- capacity: 기존 `_execution_capacity_scenario`의 `reconciled`(현금·보유수량·체결수량) True 요구
- capacity 대조: `filled_qty_total == actual_trade_filled_qty_total`
- 적용 범위: cost 9회 + capacity legacy 5회 + stability 18회 = **legacy 32회**, capacity **15회**
  전부 통과. stability는 `run_etf_strategy`를 감싸 모든 호출에서 검산을 강제한다.

## 취약점 요약

1. **세금이 비용의 지배 항목**(기준 조건 71%). 과세 ETF 비중이 높아 수수료 인하만으로는
   비용 민감도가 개선되지 않는다.
2. **운용규모 5천만원 이상 + 낮은 참여율**에서 체결률이 급락한다(1억/5% -10.2%, 10억/5% -36.2%).
   실패는 부분취소로 확정되며(10억/1% 152건), 미체결분이 목표 비중에서 빠진다.
3. MDD(-51~-52%)는 비용·유동성 조건과 무관하게 유지된다. 즉 스트레스는 **수익률만** 깎고
   낙폭 위험은 줄이지 않는다.
4. 3종목 분산은 고비용 구간에서 회전 비용으로 상쇄되어 중앙(2종목) 대비 우위가 사라진다.

## 남은 한계

- OHLCV capacity는 **가정 기반 진단**이며 실제 주문·체결 증거가 아니다(부분체결/이월/취소
  정책의 모의 결과). `executable_fill_claim=False`.
- 참여율은 bar volume 대비 고정 비율이며, 호가 깊이·큐·시장충격을 모형화하지 않는다.
- 거래비용 2x/3x는 수수료·세금에만 적용했다. 스프레드·슬리피지는 별도 축으로만 움직였다.
- `est_gross_final`은 비용을 단순 가산한 근사치다(복리 효과 미반영).
- PIT·기업행위·분배금 승인 blocker는 그대로 유지된다(`docs/backtest-integrity.md`).
- 유니버스 16종·`price` 기준·현행 동결 설정만 검증했다. NAV/total-return 기준과
  실데이터 결측/거래정지 구간은 별도 검증 대상이다.
